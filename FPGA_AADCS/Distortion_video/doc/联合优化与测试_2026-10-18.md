## 已完成的 FPGA 实现

| 文件 | 作用与边界 |
| --- | --- |
| `source/rtl/store.v` | 组合frame和burst，检查帧首尾、拍数、帧号；坏帧/abort用零补齐剩余写入后丢弃；无空槽时丢帧；等待显式fence_ack再发布 |
| `source/rtl/fetch.v` | 28位字节地址、128位读数据；预留完整1～16拍缓冲后才发AR；按4KiB边界拆分；吸收无RREADY的返回，检查RLAST和多余响应 |
| `source/rtl/supply.v` | 单时钟整描述符预存，16～4096字节，读请求后一拍同步返回；作为独立测试模块保留 |
| `source/rtl/bridge.v` | 在DDR写钟和PCIe读钟间交接完整描述符；双时钟RAM、发布/回收翻转握手；全部数据准备好后才允许launch；错误同步返回写域 |
| `source/rtl/video.v` | 集成store、fetch和bridge；完整帧取得、按段取数、跨段游标推进、越界拒绝；最后源数据响应回到DDR域后释放帧槽 |

`frame/burst/split/dmapat` 保留。所有综合代码使用 `.v`，一个文件一个主模块。PDS接受 `syn_preserve` 并转为 `PAP_PRESERVE`，已替换不受支持的通用ASYNC_REG属性。

内存分配为两个外部DDR槽，默认基址0和0x400000，每帧259200个128位拍（4147200字节）。片内只保存突发/描述符缓存，没有用片内RAM存放整帧。

## 三个时钟域的契约

- 视频输入先通过现有stream/afifo进入DDR用户域；真实实时源若不能接受反压，仍需把溢出可靠地跨域传给abort，并协调复位。测试中的直接停源控制只属于testbench。
- video的帧控制、分段控制、DDR和fence信号均在clk域；dma_prepared/dma_launch/dma_read/data/valid/done在dma_clk域。
- bridge用发布/回收翻转控制双口RAM所有权。长度和RAM内容从发布至回收保持不变；共同复位必须同时取消两域和外部在途事务。不能只复位其中一个域。
- dma_done是PCIe域最后一个**源数据响应**；segment_done是其同步回DDR域的回收事件；frame_done表示该源帧已读完。三者都不是“ARM内存已经可读”的完成通知。
- fence_ack必须由DDR适配证明先前写入对后续读取已可见。当前Pango端口没有B响应，不能把burst.done直接当作此证明；本轮仿真由行为模型提供延迟确认。

## FPGA 验证

回归脚本位于副本 `sim/regress.py`。它直接调用已安装的ivlpp和ivl核心，避开Windows下iverilog驱动退出异常；每一步必须退出码0，删除旧产物后重建，不接受失败编译后的旧vvp。

23组测试覆盖：

- 原地址、插值、warp、图案、打包、异步FIFO、stream、溢出、vtop、探针、分段和frame/burst回归。
- store：两个槽的读写保护、发布前fence等待、无空槽丢帧、提前/缺失EOF、帧号变化、额外SOF、abort补零、恢复和部分帧复位。
- fetch/faults：分页、1/17/255/256/513拍、AR和输出暂停、地址与首数据同周期、提前/缺失/多余RLAST、无请求返回、越界和待发AR复位。
- supply/bridge：16/112/272/4096字节、同步响应、启动与首请求重合、欠读/超读、跨时钟握手、停止读钟、共同复位。
- pipeline/async：三个完整帧，读写不同槽同时进行，三段拼接连续性、同频与异频DMA时钟、帧越界和复位。
- source：真实pat→pack→异步FIFO→store→DDR模型→fetch→bridge→DMA响应，三个时钟、三帧彩条逐拍比较。
- replay：完整1920×1080 RGB565帧，16200个DDR写突发，按真实ARM逐行/分页算法提交2025段，259200个DMA拍全部逐拍比对，无遗漏/重复。

日志和输入SHA256位于副本 `checks/regression/summary.json` 及各测试log。

PDS 2022.2-SP6.4：store、fetch、bridge、video独立顶层综合通过；副本原vtop工程Compile通过。video独立综合报告为782 LUT、541寄存器、2 DRM、0 APM、0锁存器；双时钟缓存推断为两个GTP_DRM36K_E1。这是新增核心本身的资源，**不含完整DDR PHY/PCIe/校正系统**。

独立video暴露的是内部总线，763个端口不能当作763个板级引脚；它不是可直接布局布线/烧录的板级顶层。独立检查未施加板级完整时序约束，综合报告不能证明125MHz时序或1080p60吞吐。PDS主工程继续选用vtop，尚未实例化video与真实IP。

## ARM 修改

- 提取可离线测试的protocol.h：检查stride、帧/总缓冲大小、32位DMA地址范围，统一4KiB拆分和命令编码；SETUP失败保留errno，拒绝地址回绕。
- 采集函数传播传输/预读/等待和msync失败；重新核查Bus Master，FRAME图案选择不会在最终配置时被清掉。
- 带stride的逐行RGB565转换和字节交换，支持不对齐输入，跳过padding；小图采样不再固定读4096像素。
- 用8KiB位图在整张图片均匀采样统计不同像素，无共享静态哈希表；仍是图像启发式，不能证明链路训练、帧新鲜度或完成。
- 帧头助手移入header.c，支持RGB565字节交换前后的状态头与行头；probe小于16字节时不解析状态头。
- 显示端显式固定正在绘制的缓冲槽，生产者不能复用它；状态文本读取加锁，合并重绘回调并回收定时器/回调。
- 更新应用与测试Makefile的源码和头文件依赖。BAR1地址和命令协议不变，保留默认忙等兼容路径；未自行增加完成寄存器。

## ARM 验证

`tests/run_offline.py` 或原有 `make test` 运行四组：

1. 原单元测试32项，零失败；Windows主机只验证标量，不能声称验证AArch64 NEON。
2. contract：全部65536个RGB565值、全部256种16字节页内偏移、1080p的2025段、大小/地址边界、padding、非对齐、小图/全图采样、交换帧头及显示槽选择。
3. capture_mock：直接编译真实fpga_capture.c，以替身系统调用验证2025次命令、FRAME控制、分配/地址/配置/Bus Master/msync错误和资源清理。
4. window_mock：直接编译真实window.c，以替身GTK/cairo在绘制期间交错10000次发布，验证不覆写绘制槽、重绘合并、关闭和回调清理。

全部以GCC的-Wall -Wextra -Werror构建通过；结果和输入指纹在ARM `.cache/tests`。替身测试不证明真实内核DMA一致性、GTK运行时或显示速率；当前机器没有该工程的Linux交叉工具链/sysroot，未编译和部署真实aarch64窗口程序。
